打包：0.12 首个成品（含五语新文案）—— 两个老坑都钉进门里

用户原话：「重编吧 就是0.12jar了」（并确认扳手那个是已知小 bug、不着急修）。

**成品**：`release\PotatoST-0.12.jar` = **`45c061dfc9c171aeea783b64c05ca0e3d884871b`**
        5,769,926 B / 1181 条目（64 目录 + 1117 文件）/ 357 类 / 5 语言 / 43 成就 / 73 配方
        `.sha1` = 40 位十六进制 + \n（41 字节、无 BOM），与 `Get-FileHash`、`certutil` 两源一致

顺序不是 `build` 一把梭 —— 上一轮同一个产物栽过两次：
  ① 0.11 jar 是加文言文**之前**构建的 ⇒ 包里没有 `lzh.json`，切文言整包回落英文；
  ② `gradlew build` 报 BUILD SUCCESSFUL，产物却 **0 个 .class**（纯资源、5,041,845 B）——
     成因是打 jar 那一刻 `build/classes/java/main` 是空的（并行会话把类清了），
     证据是时间戳反向：jar 写入 11:59:57、类 mtime 12:00:27~12:00:55。

这一轮：先 `gradlew --status` 确认没有在跑的构建 → `compileJava --no-configuration-cache
--rerun-tasks` → **先核对 357 个类都在且 mtime 是刚刚**（12:56:12~14）→ **紧接着** `jar`
（5s，类目录全程没被清）→ 体检 → 发布 → 再体检**发布件本身**。

新门 `_rzh_jar012_check.py` 把两个坑钉成判据（跑在发布件上）：
  C1 `.class` 数 ≥ 基线 357（少了就是"打 jar 时输入不全"）
  C2 每个源 `.class` 的 mtime **必须早于** jar 的 mtime（反向即坑 ② 复现；实测 12:56:14 / 12:56:25）
  C3 五份 lang **逐字节**等于源目录（含 lzh），并读一次 lzh 元数据（文言 / 華夏）
  C4 zip CRC 全过 + `MODS.TOML` 里版本号必须是 0.12（实测读出来就是 0.12）
  B2 成就 / 配方**逐名**与源目录对账
⚠ B2 当场教会我一件事：`namelist` 里有 **64 个目录条目**，不排掉就会冒出
  "jar 44 份成就 / 源 43 份"这种**假差异**，我确实被骗了一次。

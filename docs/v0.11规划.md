## 0. 一句话结论

第一部分**技术上全部可行**，但踩到一个**必须先拆的雷**：本工程现有的「气体判定」是**负向**写的
（`非水非岩浆 ⇒ 气体`），一旦注册原油，**高压气罐会认原油为气体、能灌进去**。
所以实现的第一刀不是加石油，而是把这个判定**改成正向白名单**（见 §4 L1）。
另外本工程**从来没注册过液体方块**（三种气体故意没有方块），原油是第一个，检查器可能要跟着放行（§4 L3）。

## 3. 逐项技术拆解

### 3.1 原油（流体）

* 注册：`ModFluids` 新增流体类型 `potato_s_t:crude_oil` + 源 `crude_oil` + 流动 `flowing_crude_oil`，
  以及**液体方块** `potato_s_t:crude_oil`（`ModBlocks` 里注册，属本工程第一例）。
* 贴图：`textures/block/crude_oil_still.png`、`textures/block/crude_oil_flow.png`。
  你没画之前**先借原版** `minecraft:block/black_concrete`（黑色不透明，视觉上最接近原油），
  这两个文件名会进 `docs/贴图清单.md` 的「待画」。
* 渲染层：拟 `solid`（不透明，像岩浆；半透明要另说）。
* ⚠ **必须做成 `LiquidBlock`**，不只是"能装进湖里"：现有的**流体泵只认液体方块本身**
  （`FluidPumpBlockEntity:400` 的 `state.getBlock() instanceof LiquidBlock` + 源液体判定，
  每个源方块 = 1000 mB、抽干即移除方块）—— 不做成方块，泵和管道就永远抽不到原油。
  这也直接牵出一条**待你拍板**的事：**泵到底允不允许抽原油**（见 §5 待决 11）。
* 流体属性（NeoForge `FluidType.Properties`）：密度拟 800（比水轻）、黏度拟 3000；
  `canConvertToSource(false)`、`canHydrate(false)`（**不然原油会润湿耕地**）、
  `canExtinguish(false)`、`supportsBoating(false)`、`lightLevel(0)`。
  ⚠ 具体方法名以 1.21.1 反编译源码为准，实现时逐项核对，不靠记忆。
* 跨 mod 标签（**2026-09-24 ZF74 更新：从"不加"改成"挂上"**）—— 两路取证推翻了原计划：
  ① 上游 NeoForge 21.1.235 的 `Tags.java` 里**没有**原油类通用 `c:` 标签，**但有** `Tags.Fluids.GASEOUS`
     （上游 `data/c/tags/fluid/gaseous.json` 现在只挂了个 legacy 别名 `#forge:gaseous`，
     等于"等各 mod 自己挂进来"）；
  ② 现实约定：机械动力·柴油动力（`createdieselgenerators`）自带 `data/c/tags/fluid/crude_oil.json`
     ⇒ "原油"的通用名就是 **`c:crude_oil`**。
  ⇒ 本模组现在挂 5 份：`c:gaseous`（氧/氢/氯，源+流动）、`c:crude_oil`（原油，源+流动），
  外加 `c:oxygen` / `c:hydrogen` / `c:chlorine`（上游没有，但按 `c:` 命名约定补上，
  别人写 `#c:oxygen` 就能对上）。**以后每加一种流体，一律先挂 `c:` 标签**（见档案 §6.19）。

### 3.2 油桶（物品）

* 新类 `OilBucketItem extends Item`：`stacksTo(1)`；白色容量条 + Shift tooltip 的**表现**与高压气罐一致，
  但**存储语义不同**：单流体、容量 3000。
* 存储：沿用 `CUSTOM_DATA` 存档的思路，但**另写** `OilBucketContents`（单流体、3000）。
  理由：`TankContents` 是「多种气体混装 + 3500」的语义，硬改它等于动已发布的气罐代码
  （计划里明确**不动气罐**）。
* tooltip 键拟：`tooltip.potato_s_t.oil_bucket.total / .empty / .entry / .hold_shift`（四语言）。

### 3.3 「舀取」怎么实现

* 原版 `BucketItem` 只认**一种**固定流体，做不到「任何液体」⇒ 自己写：
  `use()` 里做视线射线 → 命中源方块（`LiquidBlock` / `BucketPickup`）→ 判定 `isSource()` →
  通过白名单（非气体）→ 扣掉源方块 → 往桶里加**一格 1000 mB**。
* **待你拍板**：一次右键舀 **1000 mB**（3 次装满，推荐）还是**一次舀满 3000**（一次吞 3 格）。
* 桶里已有 1000 mB 水时右键原油 ⇒ **拒绝**（你的「异种流体不可以再被灌装」）。
* 空桶右键气体？气体**没有世界方块**，根本舀不到 ⇒ 天然满足「不可以罐装气体」。
* **本轮拟不做「倒出/放置」**（你只说了舀取）：倒出要么以后跟分馏塔/储罐一起做，
  要么单开一条规则（潜行右键倒出？）—— 见 §5 待决 2。

### 3.4 灌装机（改造点，这是唯一必须碰的老代码）

现状（已核对源码）：

* 槽位校验写死 `stack.getItem() instanceof HighPressureTankItem`（`FillingMachineBlockEntity:82`）；
* 五个水箱的过滤器是 `isGasFluid(...)`，实现是「**非水非岩浆**」（`:134`）；
* 灌装逻辑同样写死 `HighPressureTankItem`（`:270`、`:295`、`:304`）;
* 界面里的流体是靠**整数 id** 同步的，而 `ModFluids.idOf/byId` **只认 3 种气体**
  （`FillingMachineBlockEntity:110`、`FillingMachineMenu:100`）。

⇒ 改造方案（拟）：

1. 判定改成**正向白名单**：`ModFluids.isGas(fluid)` = 明确列出的 3 种气体（+流动变体）。
2. 引入一个很小的容器接口（如 `FluidContainerItem`：`capacity()` / `accepts(Fluid)` /
   `space(stack)` / `fill(stack, fluidStack, max)` / `isEmpty(stack)`），
   让**高压气罐**和**油桶**都实现它，灌装机的槽位与灌装逻辑只认接口。
3. 水箱过滤器：拟**不限流体**（容器自己负责拒收）——否则油桶在机器里根本灌不到油。
   「高压气罐只进气体、油桶只进液体」这条规矩由**容器**把关，不由机器把关。
4. 界面流体同步：把 `idOf/byId` 换成「流体注册 id」或给原油留一个 id，否则机器里装了原油，
   界面会显示成**空**（这是最容易漏的一个坑）。
